# 아이디어를 AI로 검증하고 설계하기

## 아이디어 → 프리토타이핑 → 설계

> 이 문서는 **아이디어를 다듬는 단계에서 AI 에이전트(Gemini CLI / Claude Code)를 어떻게 쓸 수 있는지**를 다루는 실습 자료입니다.
>
> 목표는 “큰 서비스를 바로 완성하기”가 아닙니다.  
> **만들기 전에, 만들 가치가 있는지 가볍게 확인하고, 그다음 만들 수 있는 형태로 정리하는 것**이 목표입니다.

---

## 0. 출발점

지금까지 우리는 CLI 에이전트로 **무언가를 만드는 법**을 익혔습니다.

이번에는 그 앞 단계, 즉 **만들기 전에 던지는 질문**을 AI와 함께 다뤄봅니다.

아이디어가 떠오르면 본능적으로 이렇게 생각하기 쉽습니다.

> “좋은데? 바로 만들어보자.”

그런데 그 사이에 질문을 두 개만 끼워 넣어보겠습니다.

1. **이거, 만들 가치가 있나?**  
   _Should we build it?_
2. **만든다면 어떻게 만들까?**  
   _How would we build it?_

AI는 두 질문 모두에서 도움이 됩니다.  
다만 **단계마다 AI를 쓰는 방식이 다릅니다.**

이 문서의 핵심은 그 차이를 익히는 것입니다.

---

## 1. 큰 흐름

```text
[1] 아이디어        →   [2] 프리토타이핑        →   [3] 설계
  가설 한 문장          만들 가치가 있나?           만든다면 어떻게?
                       Should we build it?        How would we build it?
```

| 단계 | 던지는 질문 | AI가 거드는 일 |
|---|---|---|
| 1. 아이디어 | 어떤 문제를 풀고 싶은가? | 막연한 생각을 검증 가능한 가설로 바꾸기 |
| 2. 프리토타이핑 | **만들 가치가 있나?** | 아주 작은 검증 도구 만들기, 반응 데이터 정리하기 |
| 3. 설계 | **만든다면 어떻게?** | 기능 분해, 서비스 흐름, 폴더 컨텍스트, 에이전트 역할 정리하기 |

중요한 순서는 이것입니다.

> **Should**를 먼저 보고, 그다음 **How**로 넘어갑니다.

가치를 따져보기 전에 설계부터 들어가면, **안 만들어도 될 것을 너무 정성껏 설계하게 될 수 있습니다.**

## 2. 프리토타이핑이 뭔가요?

**프리토타이핑(Pretotyping)**은 구글 출신 알베르토 사보이아(Alberto Savoia)가 발전시킨 아이디어 검증 방법입니다.

발음은 프로토타이핑과 비슷하지만, 묻는 질문이 다릅니다.

| 구분 | 프리토타입 Pretotype | 프로토타입 Prototype |
|---|---|---|
| 핵심 질문 | **Should we build it?** 만들 가치가 있나? | Can we build it? 만들 수 있나? |
| 시점 | 만들기 전 | 만드는 중 |
| 목적 | 실제 수요와 관심 확인 | 기능과 기술 가능성 확인 |
| 비용 | 매우 작게 | 상대적으로 큼 |
| 모토 | **Fake it before you make it** | Make it work |
| 좋은 결과 | 계속할지, 멈출지, 방향을 틀지 판단 | 어떻게 구현할지 개선 |

프리토타이핑은 “가짜로 속이자”가 아닙니다.  
정확히는 **큰 비용을 들이기 전에, 가장 작은 실험으로 실제 반응을 확인하자**는 접근입니다.

### PalmPilot의 나무토막 사례

프리토타이핑에서 자주 소개되는 사례가 있습니다.

PalmPilot을 만들기 전, 창업자 Jeff Hawkins는 실제 전자기기를 만들기 전에 **셔츠 주머니에 들어가는 나무토막**을 들고 다녔다고 알려져 있습니다. 일정 확인이 필요한 순간마다 그 나무토막을 꺼내 마치 기기처럼 써보며, “이런 물건이 내 일상에 정말 필요한가?”를 확인한 것입니다.

코드도 없고, 배터리도 없고, 화면도 없습니다.  
하지만 중요한 질문은 확인할 수 있었습니다.

> “이런 경험이 실제 생활에서 쓸모가 있는가?”

이것이 프리토타이핑의 감각입니다.

## 3. 도시·어반테크 아이디어에 적용하면?

도시 문제나 SDGs 아이디어는 처음에는 대개 크게 시작합니다.

- “도시 쓰레기 문제를 해결하고 싶다”
- “교통약자를 돕고 싶다”
- “동네 에너지 절약 서비스를 만들고 싶다”
- “도시 데이터를 활용한 지속가능성 서비스를 만들고 싶다”

좋은 출발이지만, 바로 만들기에는 너무 큽니다.

프리토타이핑에서는 이런 큰 아이디어를 **검증 가능한 작은 질문**으로 줄입니다.

| 큰 아이디어 | 프리토타이핑 질문 |
|---|---|
| 주차 공유 앱 | 사람들이 실제로 “빈 주차공간 알림 신청” 버튼을 누를까? |
| 동네 데이터 리포트 | 사람들이 손으로 만든 샘플 리포트를 읽고 다음 리포트를 신청할까? |
| 폐기물 수거 매칭 | 자동화 없이 단톡방/폼으로 수동 매칭해도 사람들이 이용할까? |
| 에너지 절약 서비스 | 사용자가 자신의 생활 습관을 입력하고 절약 미션을 받아볼까? |
| 교통약자 이동 안내 | 사용자가 이동 상황을 입력하면 위험/불편 요소 안내를 유용하다고 느낄까? |

여기서 중요한 것은 **진짜 서비스 전체를 만들지 않아도 된다**는 점입니다.

처음에는 다음 정도면 충분합니다.

- 가짜 신청 페이지
- 간단한 입력폼
- 수동으로 만든 리포트
- HTML/JavaScript 계산기
- 사람이 뒤에서 처리하는 매칭 실험
- 사용자가 누를 수 있는 버튼과 결과 화면

## 4. AI가 가장 빛나는 구간: 프리토타이핑

프리토타이핑에서 AI가 유용한 이유는 간단합니다.

> 몇 시간 걸릴 실험 도구를 몇 분 안에 만들 수 있기 때문입니다.

AI가 도울 수 있는 일은 다음과 같습니다.

| 필요한 일 | AI가 도울 수 있는 방식 |
|---|---|
| 가설 정리 | 막연한 아이디어를 한 문장 가설로 바꿈 |
| 검증 방법 고르기 | Fake Door, Wizard of Oz, Concierge 중 무엇이 적합한지 제안 |
| 화면 만들기 | 랜딩페이지, 신청폼, 안내 페이지 초안 생성 |
| 질문 만들기 | 인터뷰 질문, 설문 문항, 관찰 체크리스트 생성 |
| 데이터 정리 | 클릭 수, 신청 수, 인터뷰 메모를 표로 정리 |
| 다음 판단 | 계속/수정/중단 중 어느 방향이 나은지 토론 상대가 됨 |

하지만 AI에게 맡기면 안 되는 것도 있습니다.

### AI가 대신할 수 없는 것

AI는 실제 사람의 반응을 대신할 수 없습니다.

예를 들어 이런 말은 신호가 약합니다.

> “AI에게 가상 사용자 1,000명을 시뮬레이션했더니 90%가 좋다고 했습니다.”

이건 실제 검증이라기보다는 **상상 속 반응**에 가깝습니다.

프리토타이핑에서 더 강한 신호는 이런 것입니다.

- 누군가 버튼을 눌렀다
- 이메일을 남겼다
- 폼을 제출했다
- 다시 써보겠다고 했다
- 시간을 내서 인터뷰에 응했다
- 샘플 리포트를 받고 다음 리포트를 요청했다
- 실제 상황에서 사용해보고 불편함을 말했다

정리하면:

> **AI의 의견보다 사람의 행동이 더 강한 증거입니다.**

## 5. 자주 쓰는 프리토타이핑 방법

### 1) Fake Door: 가짜 문

아직 기능이나 서비스가 없지만, 마치 있는 것처럼 버튼이나 신청 페이지를 둡니다.

예:

- “분리배출 진단 신청하기” 버튼
- “우리 동네 탄소 리포트 받아보기” 버튼
- “교통약자 이동 위험도 분석 시작하기” 버튼

버튼을 누르면 이렇게 안내할 수 있습니다.

> “현재 준비 중인 서비스입니다. 관심 등록을 해주시면 테스트 참여 안내를 보내드리겠습니다.”

확인할 수 있는 것:

- 사람들이 관심을 보이는가?
- 어떤 문구에 더 반응하는가?
- 어떤 문제 설명이 더 설득력 있는가?

주의할 점:

- 사람을 속여서 피해를 주면 안 됩니다.
- 민감한 개인정보를 받지 않습니다.
- 공공기관이나 실제 서비스처럼 오해하게 만들지 않습니다.
- 테스트 목적임을 적절한 시점에 알려야 합니다.

---

### 2) Wizard of Oz: 오즈의 마법사

겉으로는 자동화된 서비스처럼 보이지만, 뒤에서는 사람이 수동으로 처리합니다.

예:

- 사용자가 폐기물 사진 설명을 입력한다.
- 시스템이 자동 분류하는 것처럼 보인다.
- 실제로는 사람이 Gemini/Claude와 함께 분류 결과를 만들어 보낸다.

확인할 수 있는 것:

- 사용자가 이런 흐름을 편하다고 느끼는가?
- 자동화가 되기 전에 서비스 가치가 있는가?
- 어떤 입력이 자주 들어오는가?

---

### 3) Concierge: 컨시어지

아예 사람이 직접 서비스를 제공합니다.

예:

- “동네 지속가능성 리포트”를 자동 생성하지 않고, 사람이 3명에게 직접 만들어준다.
- “맞춤형 에너지 절약 미션”을 앱이 아니라 사람이 직접 보내준다.
- “교통약자 이동 안내”를 데이터 시스템 없이 직접 조사해서 알려준다.

확인할 수 있는 것:

- 사람들이 결과를 실제로 유용하게 느끼는가?
- 어떤 부분을 가장 좋아하거나 불편해하는가?
- 자동화할 가치가 있는 반복 작업이 있는가?

---

### 4) Manual-first Report: 손으로 만든 첫 리포트

도시 데이터 서비스에 특히 잘 맞습니다.

처음부터 데이터 대시보드를 만들 필요는 없습니다.  
엑셀, 공공데이터, 검색 자료, AI 요약을 조합해서 **샘플 리포트 1개**를 만들어볼 수 있습니다.

예:

- “우리 동네 폭염 취약도 간단 리포트”
- “캠퍼스 주변 보행 안전 체크 리포트”
- “분리배출 혼동 품목 TOP 10 리포트”

확인할 수 있는 것:

- 사람들이 리포트를 읽는가?
- 다음 리포트를 요청하는가?
- 어떤 정보가 실제 의사결정에 도움이 되는가?

---

### 5) Paper / Role-play: 종이 또는 역할극

서비스 화면을 종이에 그리거나, 팀원들이 사용자와 시스템 역할을 나눠 연기합니다.

예:

- 한 명은 시민 사용자
- 한 명은 AI 상담봇
- 한 명은 도시 정책 담당자
- 한 명은 데이터 시스템

확인할 수 있는 것:

- 서비스 흐름이 자연스러운가?
- 사용자가 어디서 막히는가?
- 어떤 입력과 출력이 필요한가?

## 6. 좋은 가설 한 문장 만들기

아이디어는 먼저 한 문장 가설로 줄입니다.

템플릿:

```text
[누가]는 [어떤 상황/문제] 때문에 [무엇]을 필요로 할 것이다.
```

예시:

```text
자취생은 분리배출 방법을 헷갈리는 상황 때문에,
품목을 입력하면 버리는 방법을 알려주는 간단한 도구를 필요로 할 것이다.
```

```text
버스 정류장까지 이동이 어려운 고령자는 외출 전 이동 불편 요소를 알고 싶기 때문에,
이동 목적과 시간대를 입력하면 주의사항을 알려주는 안내 도구를 필요로 할 것이다.
```

```text
동네 상권을 고민하는 소상공인은 주변 유동인구와 날씨 변화가 매출에 미치는 영향을 알고 싶기 때문에,
간단한 지역 리포트를 받아보는 서비스를 필요로 할 것이다.
```

좋은 가설은 다음 조건을 가집니다.

- **누가** 쓰는지 보인다.
- **어떤 상황**에서 쓰는지 보인다.
- 사용자가 **무엇을 입력하거나 행동할지** 상상된다.
- 어떤 반응을 보면 “관심이 있다”고 말할 수 있는지 보인다.

## 7. 이 Gemini CLI 키트는 왜 쓰나요?

이 키트는 AI에게 단순히 “코드 짜줘”라고 하기 위한 도구가 아닙니다.

목적은 다음과 같습니다.

> **아이디어를 검증 가능한 형태로 줄이고, 그 과정을 프로젝트 폴더 안에 남기기 위해서**

AI 에이전트는 기억력이 좋아 보이지만, 대화가 길어지면 맥락이 흐려질 수 있습니다.  
그래서 프로젝트 폴더 안에 다음을 남겨둡니다.

- 어떤 문제를 다루는지
- 누구를 위한 아이디어인지
- 어떤 SDG와 연결되는지
- 무엇을 검증하려는지
- 어떤 프리토타입을 만들었는지
- 어떤 반응 데이터를 보려고 하는지
- 다음에 설계한다면 무엇을 만들지

이 폴더가 잘 정리되어 있으면, Gemini CLI나 Claude Code가 같은 맥락을 계속 읽고 작업할 수 있습니다.

쉽게 말하면:

> **프로젝트 폴더는 AI 에이전트에게 주는 작업 설명서입니다.**

## 8. 키트의 기본 구성

키트를 풀면 대략 이런 구조를 보게 됩니다.

```text
my-urban-project/
├── GEMINI.md
├── project/
│   ├── 01-idea.md
│   ├── 02-service-loop.md
│   ├── 03-sdg-map.md
│   ├── 04-stakeholders.md
│   ├── 05-prototype-spec.md
│   ├── 06-build-plan.md
│   ├── 07-demo-scenario.md
│   ├── 08-reflection.md
│   └── pitch.md
├── evidence/
│   ├── assumptions.md
│   ├── sources.md
│   └── data-notes.md
├── prototype/
│   └── README.md
└── .gemini/
    ├── commands/urban/
    ├── agents/
    └── skills/
```

처음 보면 파일이 많아 보일 수 있습니다.  
하지만 학생이 직접 전부 외울 필요는 없습니다.

핵심은 세 폴더입니다.

| 폴더 | 의미 |
|---|---|
| `project/` | 아이디어, 서비스 흐름, 설계 메모 |

## 10. 가장 추천하는 사용 순서

처음부터 모든 명령을 쓸 필요는 없습니다.  
아래 순서만 따라가도 충분합니다.

```text
/urban:scope
→ /urban:service-loop
→ /urban:prototype
→ /urban:demo-review
→ /urban:pitch
```

| 명령 | 언제 쓰나 | 결과 |
|---|---|---|
| `/urban:scope` | 아이디어를 처음 줄일 때 | 가설, 사용자, 검증할 질문 정리 |
| `/urban:service-loop` | 서비스처럼 작동하는지 확인할 때 | 입력 → 처리 → 출력 → 다음 행동 흐름 정리 |
| `/urban:prototype` | 아주 작은 실험 도구를 만들 때 | HTML/JS, Streamlit, 간단한 CLI 도구 등 |
| `/urban:demo-review` | 친구에게 보여주기 전 점검할 때 | 시연 흐름, 부족한 점, 개선 방향 정리 |
| `/urban:pitch` | 아이디어를 짧게 설명할 때 | 1페이지 설명 초안 |

조금 더 설계로 넘어가고 싶다면 다음 명령을 추가로 씁니다.

```text
/urban:spec
/urban:plan
/urban:context-audit
```

| 명령 | 의미 |
|---|---|
| `/urban:spec` | 만든다면 어떤 기능과 범위가 필요한지 정리 |
| `/urban:plan` | 작은 구현 계획으로 나누기 |
| `/urban:context-audit` | AI에게 주는 프로젝트 맥락이 충분한지 점검 |

## 11. 사용 예시 1: 분리배출 도우미

처음 아이디어:

```text
도시 쓰레기 문제를 해결하고 싶다.
```

너무 넓습니다.  
Gemini CLI에서 이렇게 시작합니다.

```text
/urban:scope "자취생이 분리배출을 헷갈리지 않도록 돕는 아이디어"
```

AI가 다음과 같이 좁혀줄 수 있습니다.

```text
가설:
자취생은 분리배출 품목을 헷갈리는 상황 때문에,
품목명을 입력하면 배출 방법과 주의사항을 알려주는 간단한 도구를 필요로 할 것이다.
```

그다음 서비스 흐름을 만듭니다.

```text
/urban:service-loop
```

서비스 루프 예시:

```text
입력: 사용자가 버릴 품목과 오염 여부를 입력한다.
처리: 품목 종류와 오염 여부에 따라 분리배출 방법을 분류한다.
출력: 배출 방법, 주의사항, 오늘의 분리배출 점수를 보여준다.
다음 행동: 사용자는 '처리 완료'를 누르거나 다른 품목을 검색한다.
```

프리토타입으로는 이렇게 만들 수 있습니다.

```text
/urban:prototype "단일 HTML 페이지로 만들어줘. 입력창, 품목 선택, 결과 영역이 있고 입력에 따라 안내가 달라지게 해줘."
```

이때 중요한 것은 “진짜 완벽한 분리배출 시스템”이 아닙니다.

중요한 질문은 이것입니다.

> 사람들이 품목을 입력하고 결과를 확인하는 흐름을 실제로 유용하다고 느끼는가?

- 다른 동네/상황으로 다시 입력해보는가?

## 13. 사용 예시 3: 동네 지속가능성 리포트

처음 아이디어:

```text
도시 데이터를 활용해서 지속가능성 정보를 제공하고 싶다.
```

프리토타이핑 관점에서는 처음부터 거대한 대시보드를 만들 필요가 없습니다.

먼저 이렇게 줄입니다.

```text
/urban:scope "사람들이 자기 동네의 지속가능성 요약 리포트를 받아보고 싶어 하는지 확인하고 싶다."
```

프리토타입 방법:

- 간단한 신청 페이지를 만든다.
- 사용자가 관심 있는 동네와 관심 주제를 선택한다.
- 실제 자동 분석 대신, 1~3명에게 수동으로 샘플 리포트를 만들어준다.
- 다시 받아보고 싶은지 묻는다.

Gemini CLI 명령 예시:

```text
/urban:prototype "동네 이름, 관심 주제, 이메일 대신 임시 닉네임을 입력받는 Fake Door 페이지를 만들어줘. 개인정보는 받지 않게 해줘."
```

이 실험에서 볼 것은 “기술적으로 대시보드를 만들 수 있나?”가 아닙니다.

볼 것은 이것입니다.

> 사람들이 자기 동네 리포트에 실제 관심을 보이는가?

## 14. 의견과 행동을 구분하기

프리토타이핑에서 가장 중요한 구분입니다.

| 약한 신호 | 강한 신호 |
|---|---|
| “괜찮은 것 같아요” | 버튼을 눌렀다 |
| “나중에 쓰고 싶어요” | 알림 신청을 했다 |
| “좋은 아이디어네요” | 시간을 내서 테스트했다 |
| “필요할 것 같아요” | 실제 정보를 입력했다 |
| AI가 가상 사용자 반응을 만들어줌 | 실제 사람이 행동함 |

물론 처음에는 약한 신호도 도움이 됩니다.  
하지만 아이디어를 계속 밀고 갈지 판단할 때는 **행동 데이터**를 더 중요하게 봅니다.

행동 데이터 예시:

```text
- 랜딩페이지 방문 수
- 버튼 클릭 수
- 관심 등록 수
- 폼 제출 수
- 인터뷰 참여자 수
- 다시 사용해본 횟수
- 샘플 리포트를 요청한 사람 수
- 사용자가 남긴 구체적인 불편/개선 의견
```

## 15. AI에게 이렇게 말하면 좋습니다

### 좋은 요청

```text
/urban:scope "캠퍼스 주변 일회용컵 쓰레기를 줄이는 서비스를 생각 중이야. 사용자는 대학생이고, 너무 큰 플랫폼 말고 하루 안에 검증할 수 있는 프리토타입으로 줄여줘."
```

```text
/urban:prototype "가짜 신청 페이지를 HTML로 만들어줘. 사용자는 관심 주제를 선택하고 '알림 받기' 버튼을 누를 수 있어야 해. 버튼을 누르면 현재는 테스트 중이라는 안내가 나오게 해줘. 개인정보는 받지 마."
```

```text
/urban:demo-review "이 프리토타입을 친구 3명에게 보여주기 전에, 어떤 행동 데이터를 보면 좋은지 점검해줘."
```

### 아쉬운 요청

```text
좋은 아이디어 하나 만들어줘.
```

```text
완성도 높은 서비스를 만들어줘.
```

```text
내 아이디어가 성공할지 AI 사용자 1,000명으로 시뮬레이션해줘.
```

아쉬운 요청의 문제는 범위가 너무 크거나, 실제 행동 데이터와 연결되지 않는다는 점입니다.

## 16. Subagent와 Skill은 어떻게 생각하면 되나요?

처음부터 기술적으로 이해할 필요는 없습니다.  
쉽게 비유하면 다음과 같습니다.

### Subagent = 역할이 다른 조언자

예를 들어 한 프로젝트 안에서도 필요한 관점이 다릅니다.

- 도시 문제를 보는 사람
- SDG 연결을 보는 사람
- 서비스 흐름을 보는 사람
- 작게 구현하는 사람
- 데모 전에 문제를 찾는 사람
- 친구 입장에서 리뷰하는 사람

키트의 subagent는 이런 역할을 나눠둔 것입니다.

예를 들어 Gemini CLI에서 필요할 때 이런 식으로 불러볼 수 있습니다.

```text
@sdg-impact-analyst 이 아이디어가 어떤 SDG와 연결되는지, 너무 억지 연결은 아닌지 봐줘.
```

```text
@qa-demo-reviewer 이 프리토타입을 다른 학생에게 보여주기 전에 작동 흐름과 설명 부족한 점을 찾아줘.
```

### Skill = 반복 작업을 위한 작은 사용 설명서

Skill은 AI에게 “이런 작업을 할 때는 이런 기준으로 해줘”라고 알려주는 지침입니다.

예를 들어:

- 서비스 루프를 만들 때 보는 기준
- one-loop prototype을 만들 때 보는 기준
- 프로젝트 폴더 컨텍스트를 점검하는 기준
- 동료 리뷰를 할 때 보는 기준

즉, subagent와 skill은 학생이 외우는 기능이 아니라, **AI가 더 일관되게 도와주도록 넣어둔 작업 도구**입니다.

## 17. 설계 단계로 넘어가는 기준

프리토타이핑 후에는 다음 중 하나를 결정합니다.

| 판단 | 의미 |
|---|---|
| 계속 간다 | 작지만 실제 관심이나 행동이 보였다 |
| 바꾼다 | 문제는 있지만 대상 사용자나 방식이 달라져야 한다 |
| 멈춘다 | 관심이 거의 없거나 가정이 맞지 않았다 |

**멈추는 것도 실패가 아닙니다.**

프리토타이핑은 원래 이렇게 하기 위한 것입니다.

> 많이 만들기 전에, 헛수고를 줄이기.

계속 가기로 했다면 그때 설계로 넘어갑니다.

설계 단계에서 정리할 것은 다음입니다.

```text
- 핵심 사용자
- 해결하려는 문제
- 서비스 루프
- 필요한 데이터
- 가장 작은 기능
- 만들지 않을 것
- AI 에이전트에게 줄 프로젝트 맥락
- 폴더 구조
- 역할 분담
```

Gemini CLI에서는 다음 명령을 쓸 수 있습니다.

```text
/urban:spec
/urban:plan
/urban:context-audit
```

## 20. 윤리와 안전

프리토타이핑은 “가볍게 실험하자”는 뜻이지, 아무렇게나 속여도 된다는 뜻이 아닙니다.

다음 원칙을 지킵니다.

1. **사람에게 피해를 주지 않는다.**
2. **민감한 개인정보를 받지 않는다.**
3. **공공기관, 학교, 기업의 공식 서비스처럼 오해하게 만들지 않는다.**
4. **버튼 클릭 후에는 테스트 중인 서비스임을 안내한다.**
5. **실험 결과를 과장하지 않는다.**
6. **AI가 만든 내용은 사실인지 확인한다.**

특히 도시, 정책, 복지, 안전, 건강과 관련된 주제는 더 조심해야 합니다.

## 21. 자주 생기는 문제

### Q1. 코딩을 잘 못하는데 괜찮나요?

괜찮습니다.  
이번 실습의 핵심은 고급 코딩이 아니라 **아이디어를 작게 검증하는 사고방식**입니다.

HTML 한 페이지, 입력폼 하나, 버튼 하나, 수동 리포트 하나도 충분한 출발입니다.

### Q2. 꼭 작동하는 앱을 만들어야 하나요?

완성된 앱일 필요는 없습니다.  
다만 사용자가 무언가를 입력하거나 누르고, 그에 따라 다른 반응이 나오는 정도는 있으면 좋습니다.

```text
입력 → 처리 → 출력 → 다음 행동
```

이 흐름이 있으면 작은 서비스처럼 생각해볼 수 있습니다.

### Q3. 그냥 웹페이지 소개 자료를 만들면 안 되나요?

소개 자료도 도움이 됩니다.  
하지만 소개만 있으면 “서비스가 작동한다”는 느낌을 얻기 어렵습니다.

가능하면 다음 중 하나를 추가하세요.

- 신청 버튼
- 관심 등록
- 문제 진단 입력
- 점수 계산
- 추천 결과
- 샘플 리포트 요청
- 사용자 선택에 따라 달라지는 결과

### Q4. AI가 만든 코드가 안 돌아가면 어떻게 하나요?

Gemini CLI에 오류 메시지를 그대로 붙여 넣고 물어보세요.

```text
이 오류가 났어. prototype 폴더의 코드를 확인하고, 가장 단순한 방식으로 고쳐줘. 왜 고쳤는지도 설명해줘.
```

그리고 `/urban:demo-review`로 다시 점검합니다.

### Q5. 반응 데이터가 없으면 의미가 없나요?

처음에는 반응 데이터를 모으기 위한 준비까지만 해도 의미가 있습니다.  
다만 가능하다면 친구, 가족, 동료 학생 등 실제 사람 1~3명에게라도 보여주고 반응을 기록해보세요.

## 22. 마지막으로 기억할 문장

> **Fake it before you make it.**  
> 많이 만들기 전에, 만들 가치부터 가볍게 확인해봅시다.

AI는 여러분의 아이디어를 대신 검증해주지 않습니다.

하지만 AI는 여러분이 다음을 더 빠르게 하도록 도와줄 수 있습니다.

- 아이디어를 작게 줄이기
- 검증 가능한 질문 만들기
- 간단한 실험 도구 만들기
- 반응 데이터를 정리하기
- 계속할지 바꿀지 생각하기
- 만든다면 어떻게 만들지 설계하기

이번 실습의 목표는 “멋진 결과물”보다 다음 감각을 얻는 것입니다.

> **내 아이디어가 실제 사람의 행동과 만났을 때 무엇이 달라지는가?**
